# 视觉能力探针报告（P0.1 / T3）

> 2026-10-15 实测。宿主：opencode，原生 `read` 工具。
> 结论先行：**原生视觉可用，范围比预期宽；PDF 直读不可用，需降级路径。**

---

## 1. 能力边界表

| # | 测试项 | 资产 | 结果 | 说明 |
|---|---|---|---|---|
| 1 | 基础识图 | `t1_basic.png` 800×300 | **能** | 标题 + 5 条要点全读出，右上蓝色块位置正确 |
| 2 | 尺寸上限（密集图元） | `t2_dense_800/1600/2400/4000.png` | **能，到 4000px 仍未失效** | 45 节点 5×9 网格，编号 N1–N45 顺序完整，无串行错位 |
| 3 | 长图 | `t3_tall_2000/4000/8000.png` | **能，8000px 不需切片** | row 1–row 113 连续可读，首尾都在 |
| 4 | 小字 / 细线 | `t4_small_hairline_2x.png` | **能** | 8px 文字可读；0.5/0.8/1.2/1.7/2.2px 五档线宽可分辨 |
| 5 | PDF 直读 | `t5_multipage.pdf` 3 页 | **不能** | `read` 返回 `Cannot read pdf (this model does not support pdf input)` |
| 6 | 密集图元清单 | `t2_dense_1600.png` | **能** | 45 框架构图可完整列出 |

**判定汇总：6 项中 5 项通过，1 项（#5 PDF）失败。**

## 3. 结论与落地决策

### 3.1 VisionMCP：**不接入**

理由：唯一失败项是 PDF 直读，而 PDF 已有等价绕过路径（见 3.2）。
为一项可绕过的能力引入一个外部依赖、一个 API key、一条数据外传链路，不划算。
计划 §9 的降级条款写得很清楚，这里按它执行。

### 3.2 PDF / PPTX 验收：**PNG 代理回渲**

```
PDF/PPTX 交付物 → 渲染成 PNG（600dpi 或 300dpi）→ read PNG → judge
```

- `backends/png.py` 已提供 SVG→PNG。
- PDF→PNG 走 reportlab 生成时的位图副本，或 Edge headless 直接截图 HTML 页。
- PPTX→PNG 走 python-pptx 导出时同源生成位图。
- **验收报告里必须写明**：「本图为 PDF/PPTX 的位图代理，矢量内容以 PDF 本身为准」。

### 3.3 judge 派发规范（据实测数据定稿）

原生视觉比预期强，所以**不需要**为 judge 设计切片机制。但有三条硬规矩：

1. **位图目标宽度 ≤ 4000px。** 实测 4000px 密集内容仍完整，留一档余量。
2. **长图可直读，不切片。** 8000px 已验证。切片反而破坏跨区域的上下文（对齐关系、骑缝标题牌）。
3. **PDF 不许直接派给 judge。** 必须先转 PNG。转不了就标「视觉验收待完成」，不许伪造 PASS。

### 3.4 遗留风险

| 项 | 等级 | 说明 |
|---|---|---|
| 位图代理与原矢量件的细微差异（抗锯齿、字距） | 低 | 只影响 minor 级判定，major 缺陷在代理上同样可见 |
| 超 4000px 宽的极端宽图 | 低 | 论文图表实际不超 1740px（academic token 上限）；遇到再降采样 |
| 模型侧视觉能力随版本变化 | 中 | 每次大版本升级后重跑本探针，脚本在 `tests/probe_assets.py` |
