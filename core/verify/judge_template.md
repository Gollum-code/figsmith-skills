# 视觉裁判派发协议（judge_template.md）

> 裁判 = 原生 `read` 工具把图片像素直接喂给模型。**图不出本机**，零隐私风险。
> 本文件定义「怎么问」和「怎么收」，不改一句验收标准。

---

## 1. 什么时候需要裁判

跑完 `core/verify/` 三个脚本都 PASS **之后**才派裁判。脚本能抓的不许浪费裁判。

```
几何自检 → 数据一致性 → 视觉裁判 → 按像素证据修根因 → 定向复检
```

---

## 2. 派发格式（一个都不许少）

```markdown
你是 FigSmith 视觉裁判。请只依据你看到的像素作答，不推测、不脑补。

## 交付物
- 文件：<replica.png 的绝对路径>
- 域：<domain> / 图型：<chart_type> / token 集：<tokens>

## 参照物
- 参考图：<reference.png 的绝对路径，或「无」>
- 意图说明：<用户原话>

## 元素清单（生成侧声明，供你核对是否齐全）
1. <元素A：类型 + 位置 + 预期内容>
2. <元素B：...>

## 本域验收标准
<域 SKILL.md 里的 acceptance criteria 原文>

## 已知偏差白名单
- <例如：参考图为位图低分辨率，文字边缘允许锯齿>

## 你的输出（严格 JSON，不要 markdown 代码块以外的任何文字）
{
  "verdict": "PASS" | "FAIL",
  "issues": [
    {
      "severity": "major | minor",
      "what": "缺陷描述",
      "where": "图中位置（左上/中部/第三列第二个框...）",
      "evidence": "你实际看到的像素级证据（颜色、偏移量、缺失元素）"
    }
  ]
}
```

---

## 3. 判定规则

| 情况 | verdict |
|---|---|
| issues 为空 | `PASS` |
| 有 major | `FAIL` |
| 只有 minor 且都在白名单内 | `PASS`，但 minor 记录进缺陷库 |
| 只有 minor 且不在白名单 | `FAIL`（minor 会累积成 major） |

**`severity` 的界定：**
- `major` = 影响正确性或专业感：数据错、文字缺、对齐崩、对比度不足读不清、图元缺失
- `minor` = 影响精致度：间距不均、标签压线、圆角不一致、留白略胖

---

## 4. 铁律

1. **不伪造 PASS。** 裁判没跑，或裁判工具不可用，就写「视觉验收待完成」。不许填 PASS。
2. **evidence 必须是像素级事实。** 「感觉不好看」不是 evidence。「第三列第二个框比第一列同位置框右移约 12px」是 evidence。
3. **修根因，不做局部补丁。** evidence 指向 CSS/坐标/数据源，不是把那个框手动挪回去。
4. **定向复检。** 下一轮只派发上一轮 FAIL 项 + 回归点，不重跑全量。
5. **批量纪律。** 一次 3–4 张，多裁判并行。单张大图不许塞进 10 张的批次。

---

## 5. 缺陷记录（反哺 references/pitfalls.md）

每次 FAIL 都要落一条：

```markdown
### <缺陷标题>
- 域：<domain>
- 现象：<judge evidence 原文>
- 根因：<代码/CSS/数据层面的原因>
- 修法：<改哪里，为什么这样改能除根>
- 回归测试：<tests/blessed/<id>.png>
```

缺陷要**跨域可迁移**才记 —— 只在某个例子里出现一次的问题，写进那个例子的注释就够。
